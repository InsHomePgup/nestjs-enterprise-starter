# 方案三：DDD 模块化单体（按限界上下文分组）

## 核心思路

方案一、二解决的是"单个业务模块内部怎么组织"，方案三解决的是"模块变多之后，顶层目录怎么分组"。

当业务模块超过一定数量（比如超过 10-15 个），单纯的 `src/modules/*` 平铺会让人分不清哪些模块属于同一个业务领域、边界该划在哪里。DDD 的**限界上下文（Bounded Context）**给出的做法是：先按业务领域画出几个大的上下文，每个上下文是一个相对独立、内部高内聚的单元，上下文之间只通过明确定义的接口通信，顶层目录按上下文分组，上下文内部再用方案一或方案二组织模块。

这仍然是**单体应用**（一个可部署单元），不是微服务；但目录边界提前按"未来可能拆分微服务"的粒度划分，如果以后真的要拆，迁移成本会低很多，所以也叫"模块化单体"（Modular Monolith）。

## 目录结构示例

```
src/
├── contexts/
│   ├── identity/                  # 身份与访问上下文
│   │   ├── auth/                  # 方案一或方案二组织的具体模块
│   │   │   ├── auth.controller.ts
│   │   │   ├── auth.service.ts
│   │   │   └── auth.module.ts
│   │   ├── user/
│   │   │   ├── user.controller.ts
│   │   │   ├── user.service.ts
│   │   │   └── user.module.ts
│   │   └── identity.module.ts     # 聚合该上下文内所有模块，对外统一导出
│   ├── billing/                   # 计费上下文（未来业务，仅作示例）
│   │   ├── invoice/
│   │   ├── payment/
│   │   └── billing.module.ts
│   └── notification/              # 通知上下文（未来业务，仅作示例）
│       ├── email/
│       ├── sms/
│       └── notification.module.ts
├── platform/                      # 跨上下文的平台级基础设施
│   ├── prisma/
│   ├── cache/
│   └── health/
├── common/
├── config/
├── app.module.ts
└── main.ts
```

`app.module.ts` 只 import 各个上下文的顶层 module（`IdentityModule`、`BillingModule`……），不直接接触上下文内部的具体模块，保证上下文之间不会互相绕过边界依赖。

## 上下文之间如何通信

- 允许：A 上下文通过 B 上下文 `xxx.module.ts` 里 `exports` 出来的 Service/接口调用 B
- 不允许：A 上下文的代码直接 `import` B 上下文内部某个模块的 Prisma 实体或私有实现类
- 如果两个上下文需要频繁互相调用大量细节，通常说明上下文边界画得不对，需要重新考虑划分

## 优点

- 目录结构直接体现业务领域划分，新人根据目录就能大致理解系统的业务边界
- 上下文之间边界清晰，团队可以按上下文分工，减少多人协作时的目录冲突
- 如果未来某个上下文确实需要拆成独立微服务，因为它已经是一个内聚的目录树，迁移工作量远小于从平铺目录里"考古"拆分

## 缺点/局限

- 对于当前这种规模的模板项目（模块数量少）明显是过度设计，`contexts/identity/auth` 这种三层嵌套目录反而增加认知负担
- 需要团队先做一次业务领域划分（这本身是个不小的前期投入），划分错了后期调整成本也不低
- 对小团队、早期项目，收益不一定能覆盖前期的设计成本

## 什么时候值得引入

- 业务模块数量已经明显变多（两位数以上），`src/modules/*` 平铺已经让人找不清模块归属
- 团队规模变大，需要按业务线拆分负责人/小组
- 已经在认真考虑未来把某个业务域拆成独立微服务

对于当前的模板项目本身（起步阶段、模块数量少），**不建议**现在就上这套分组，更实际的路径是：先用方案一把目录理顺，等业务模块真的长到一定规模、边界开始模糊时，再引入方案三做一次目录层面的重组。
